# AI 智能体平台架构与开发规范

> 版本：2.0（精简架构基线）  
> 日期：2026-09-17  
> 场景：软件开发、短视频工作流、企业智能体部署、个人 SaaS。  
> 目标：建立独立于 DSH、LangGraph、OpenAI Agents SDK 等具体底座的产品平台。

---

## 1. 核心设计

平台采用“业务平台 + 可靠调度 + 可替换 Runtime + 独立工具”四层结构：

```text
产品层：用户、租户、项目、权限、计费、审批、资产
                         ↓
控制层：任务、工作流、调度、预算、路由、审计
                         ↓
执行层：DSH / Graph Runtime / Lightweight Runtime
                         ↓
能力层：模型、MCP 工具、沙箱、媒体服务、企业连接器
```

强制原则：

1. DSH 等底座只是执行器，不是产品数据库和业务内核。
2. 工作流控制确定性过程，Agent 只处理需要模型判断的步骤。
3. 核心工具独立部署，Runtime 插件只做协议适配。
4. 平台保存统一任务和事件；底座轨迹只作为调试附件。
5. 新旧底座可以并存，切换底座不迁移正在运行的任务。
6. 所有副作用依靠幂等、租约和补偿控制，不承诺无法证明的“恰好一次”。

## 2. 三类业务共用方式

| 业务 | 运行模式 | 核心资产 | 特殊要求 |
|---|---|---|---|
| 软件开发 | 自主 Agent + 沙箱 | 开发 Skill、工具、项目规范 | 仓库隔离、测试证据、高风险操作审批 |
| 短视频 | 确定性工作流 + 生成节点 | 分镜模板、角色资产、媒体管线 | 大文件、长任务、版权审核、费用控制 |
| 企业/个人 SaaS | 多租户控制面 + 多 Runtime | Agent 模板、连接器、数据与运营体系 | 隔离、计费、审计、配额和部署形态 |

三者共用身份、任务、工作流、工具、模型、资产、计量、审批和审计。业务差异通过领域模块与版本化模板实现，不复制平台内核。

### 2.1 软件开发

```text
需求 → 读取规范 → 隔离工作区 → 修改 → 测试 → 审查 → 人工授权 → 提交/部署
```

- DSH 优先承担代码、文件、Shell、浏览器和桌面操作。
- Git 提交、推送、生产部署、数据库写入是独立权限。
- 每次交付必须关联变更、测试结果、截图或日志等证据。

### 2.2 短视频

```text
选题 → 剧本 → 分镜 → 角色/场景资产 → 图片/音频/视频生成
→ 合成 → 质量与合规审核 → 人工批准 → 发布 → 数据复盘
```

- 工作流引擎掌握步骤、版本、重试和审批；Agent 负责创意与判断。
- 图片、视频和音频存对象存储，任务事件只保存引用。
- 角色、镜头和成片保留来源、参数、授权和派生关系。
- 发布和付费生成使用幂等键，防止重复扣费或重复发布。

### 2.3 企业与个人 SaaS

- 共用同一权限和计费内核；企业版增加组织、SSO、审计、数据区域和专属部署。
- 个人版提供订阅、额度、BYOK、模板、定时任务和数据删除。
- 企业私有部署使用相同制品和配置模型，不维护独立代码分支。

## 3. 平台领域边界

| 领域 | 权威职责 | 不负责 |
|---|---|---|
| Identity/Tenant | 用户、组织、角色、策略、SSO | Agent 执行 |
| Project | 项目及成员、数据范围 | 文件二进制存储 |
| Agent Registry | Agent、Skill、Tool、Workflow 的定义与版本 | 运行状态 |
| Task Control | Task、Run、Step、调度、取消、预算 | 模型内部循环 |
| Runtime Gateway | 能力匹配、适配和事件转换 | 租户与计费权威 |
| Model Gateway | 模型路由、限流、密钥、用量 | 工作流推进 |
| Tool Gateway | 工具注册、授权、调用和审计 | 业务权限解释 |
| Asset | 文件、媒体、版本、授权与派生链 | Agent 调度 |
| Billing | 预留、计量、结算、退款和对账 | 修改任务事实 |
| Audit | 不可变安全和管理事件 | 通用诊断日志 |

模块早期可部署为模块化单体，但数据库所有权和接口边界必须保持。禁止多个模块任意修改同一权威表。

## 4. Task、Run、Step 三层状态

- **Task**：用户要完成的业务目标，生命周期跨多次执行。
- **Run**：Task 的一次执行尝试，绑定 Runtime、版本和预算。
- **Step**：Run 内的模型调用、工具调用、审批或工作流节点。

```text
Task
├── Run 1（DSH 版本 A，失败）
└── Run 2（DSH 版本 B，成功）
    ├── Step：模型规划
    ├── Step：工具调用
    ├── Step：等待审批
    └── Step：生成产物
```

状态基线：

```text
Task: PENDING → ACTIVE → SUCCEEDED / FAILED / CANCELLED
Run:  QUEUED → RUNNING → WAITING → SUCCEEDED / FAILED / CANCELLED
Step: READY → RUNNING → WAITING → SUCCEEDED / FAILED / SKIPPED
```

- `WAITING` 必须标明审批、外部回调、资源、限流或定时。
- `FAILED` 必须包含稳定错误码、失败阶段和可重试性。
- Task 成功由业务验收条件决定，不以模型停止生成作为成功依据。

命令表达启动、取消、批准和重试意图；事件表达已发生事实，只追加、不覆盖。Task Control 是状态唯一写入口，Runtime 只能上报执行事实。任务内事件按 `sequence` 排序，跨任务不追求全局顺序。

## 5. Runtime 抽象与选择

### 5.1 能力声明

每个 Runtime 必须声明：

- 支持的模型和多模态类型。
- 是否支持流式、暂停、恢复、分叉、子 Agent、人工介入。
- 沙箱类型、操作系统、文件和网络能力。
- 最大时长、上下文、并发和产物大小。
- 事件完整度、检查点语义和版本兼容范围。

调度器按任务所需能力匹配；缺少强制能力时快速失败，不静默降级。

### 5.2 适配接口

```ts
interface AgentRuntimeAdapter {
  describe(): RuntimeCapabilities;
  start(input: RunInput): Promise<RuntimeRun>;
  signal(runId: string, signal: RuntimeSignal): Promise<void>;
  stream(runId: string, cursor?: string): AsyncIterable<RuntimeEvent>;
  snapshot(runId: string): Promise<RuntimeSnapshot>;
}
```

统一接口只覆盖共同语义。底座特有能力通过显式 capability extension 暴露，禁止塞入无类型 `metadata` 后让业务代码判断。

### 5.3 默认路由

| 任务 | Runtime |
|---|---|
| 代码、文件、Shell、浏览器、电脑操作 | DSH |
| 确定性图、循环、审批、长状态流程 | LangGraph 或工作流引擎 |
| 短对话、在线接口、少量工具 | 轻量 Agent Runtime |
| 媒体生成、转码、构建 | 专用 Worker，不启动 Agent 循环 |

### 5.4 版本与迁移

- Run 创建时锁定 Runtime、插件、模型策略、Skill 和 Tool 版本。
- 旧版本停止新流量后，仍保留到已有 Run 完成或达到迁移期限。
- 只有底座明确支持兼容恢复时才迁移检查点；否则从业务检查点创建新 Run。
- 不把某底座的私有推理轨迹强行转换成另一底座内部状态。

## 6. 工作流、Agent、工具和插件

```text
工作流：决定必须经过哪些步骤
Agent：在受限范围内决定如何完成某一步
工具：执行具体读取或副作用
策略引擎：决定某次调用是否允许
```

付款、发布、删除、授权和生产变更不得仅由 Agent 自主决定。

每个工具必须声明输入输出 Schema、版本、所有者、读写属性、风险等级、权限、幂等能力、超时、重试、补偿、数据范围、密钥范围和成本。

```text
Runtime → Tool Gateway → 鉴权/策略/审批 → Tool Service → 审计与结果
```

Creator、Git、浏览器、媒体生成和企业连接器优先做成 MCP/HTTP/队列服务；Runtime 内只保留薄适配器。

插件能在执行面运行代码，必须记录来源、许可证、维护者、摘要、签名、权限清单和兼容版本。安装前扫描，启用前审批，运行时隔离，并能追踪到使用它的 Run。用户插件与平台插件不得运行在同一高权限 Worker 池。

## 7. 可靠执行与横向扩展

### 7.1 状态与计算分离

- API、Runtime Gateway 和普通 Worker 尽量无状态。
- Task/Run/Step、检查点和租约写权威存储。
- 大产物写对象存储，队列只传标识和引用。
- Worker 按能力池扩容：代码沙箱、浏览器、CPU 媒体、GPU 媒体、企业专属。

### 7.2 投递与幂等

分布式任务采用至少一次投递：

- 每个副作用携带稳定 `operationId`。
- 每次尝试使用独立 `attemptId`。
- 工具保存幂等结果或拒绝重复操作。
- 数据状态与消息投递使用 Outbox 或等价机制。
- 无法幂等的动作执行前审批，失败后人工确认。

### 7.3 租约与取消

- Worker 获取有限期租约和 fencing token。
- 失去租约后不得提交新状态或副作用结果。
- 取消是持久化信号，不依赖进程内变量。
- 外部任务无法立即取消时进入 `CANCELLING`，后续步骤不得启动。

### 7.4 调度与背压

调度考虑能力、数据区域、租户等级、预算、优先级、等待时间和供应商限流。过载时延后批处理、停止非关键重试、限制低等级新任务，并返回明确排队状态。

出现长任务、人工等待和多 Worker 协作后，引入 Temporal 或等价可靠工作流引擎。早期可以使用具备租约、Outbox 和恢复能力的数据库队列，但接口必须可替换。

## 8. 多租户与部署

三种部署级别：

1. **共享 SaaS**：共享服务，数据行级或库级隔离。
2. **专属 Cell**：共享全局控制面，独立执行面、数据库、存储和密钥。
3. **客户云/本地**：控制面和执行面均在客户环境。

```text
Global Control Plane
├── Cell A：个人与小团队
├── Cell B：企业专属
└── Cell C：指定数据区域
```

Cell 之间不共享运行数据和密钥。`tenantId` 由认证上下文注入，覆盖数据库、缓存键、队列、向量索引、对象路径、密钥、日志和指标；客户端提供的租户标识不能决定访问范围。

私有部署使用相同版本制品和配置模型，不建立客户专属源码分支；升级前检查数据库、插件、Runtime 和工作流兼容性，并支持备份、恢复、密钥轮换和审计导出。

## 9. 数据、安全与成本

### 9.1 数据权威

- PostgreSQL：租户、定义版本、任务、审批、计费和索引元数据。
- 对象存储：代码快照、图片、音频、视频、构建包和报告。
- Event Store：平台统一事件。
- Runtime Trace Store：底座原始轨迹，按保留策略管理。
- Redis：缓存、限流和短期协调，不作唯一权威。

知识库继承源数据权限；删除源数据时同步清理索引、缓存和派生摘要。

### 9.2 安全

- 外部网页、文档、代码和工具返回均视为不可信数据。
- 权限由代码和策略引擎判断，不采信模型文本结论。
- 沙箱默认禁止宿主机、用户主目录、Docker Socket 和无边界网络。
- 密钥通过 KMS/Vault 以短期凭证注入，不进入提示词、日志或产物。
- 高风险调用实施最小权限、审批、审计和可撤销授权。

### 9.3 计量

统一记录模型 Token、媒体生成、工具费用、沙箱资源、存储和流量：

```text
预算检查 → 额度预留 → 使用事件 → 实际结算 → 释放余额 → 对账
```

价格版本和历史流水不可覆盖。Task 达到金额、Token、轮次或时间预算后必须停止或等待追加授权。

## 10. 可观测性与质量

所有链路关联 `tenantId`、`taskId`、`runId`、`stepId`、`traceId`、`operationId` 以及 Runtime、模型和工具版本。

核心指标：排队与执行时延、成功率、每 Task 的轮次/Token/费用、人工介入率、各依赖失败分布、软件任务返工率、短视频可用镜头成本和越权拒绝事件。

发布门禁：

1. Runtime、模型、工具和媒体 Provider 契约测试。
2. 权限、状态机、计费和工作流确定性测试。
3. 固定任务集上的正确性、成本和安全评测。
4. 重复消息、Worker 中断、限流和存储故障注入。
5. 从用户入口到产物、审批和费用的真实 E2E。
6. 数据库、缓存、检索、对象和日志的租户隔离测试。

升级 Runtime 或插件必须锁定版本、通过同一评测集、灰度新任务并保留旧 Worker；禁止浮动最新版直接上线。

## 11. 实施顺序

### 阶段一：平台内核

- Task/Run/Step 与统一事件。
- Identity/Tenant、权限、审批和基础计量。
- Model Gateway、Tool Gateway 和 Runtime Adapter。
- DSH 执行一个真实软件开发任务。
- 工作流执行一个脚本到分镜任务。

完成标准：更换模型或新增 Runtime 不修改产品领域代码。

### 阶段二：内部生产

- 软件开发形成修改、测试、审查和授权闭环。
- 短视频形成素材、生成、审核和版本闭环。
- 沙箱、对象存储、预算、审计和故障恢复可用。
- 真实内部任务持续评测，不依赖人工改数据库恢复。

### 阶段三：个人 SaaS

- 订阅、额度、支付、对账和用量明细。
- 多用户隔离、队列、限流、通知和数据删除。
- 模板、定时任务、BYOK 和 API。

### 阶段四：企业版

- 组织、SSO、企业审批、知识库和连接器。
- 专属 Cell、客户云部署、备份恢复和升级演练。
- 数据区域、保留策略、审计导出和 SLA。

暂缓自研通用 Runtime、开放插件市场、跨底座迁移执行中检查点，以及没有可量化收益的多 Agent 角色。

## 12. 开发前必须验证

1. DSH 中断后能否从业务检查点安全创建新 Run？
2. 同一个 Tool 能否被 DSH 和另一 Runtime 无差异调用？
3. 重复投递是否会造成重复提交、扣费或发布？
4. Workflow 等待人工一天后能否在重启后继续？
5. 撤销权限后，排队和运行中的任务是否立即失去能力？
6. 企业租户能否证明数据、密钥、日志和索引没有跨 Cell 泄露？
7. 模型故障时，哪些任务允许降级，哪些必须停止？
8. Runtime 升级后，旧 Run 和插件保留多久？
9. 短视频任务的真实毛利能否按步骤计算？
10. 软件任务成功是否由测试与验收证明，而非模型自报？

这些问题没有可执行答案前，不进入公开多租户 SaaS。

## 13. 架构验收

- [ ] 产品代码不依赖具体 Runtime 内部类型。
- [ ] Task、Run、Step 和底座 Trace 职责分离。
- [ ] Runtime 能力不足时快速失败，不静默降级。
- [ ] 工具由统一网关鉴权，Runtime 无法绕过。
- [ ] 副作用具备幂等键、审计和必要补偿。
- [ ] 新旧 Runtime 能并存并逐步切流。
- [ ] 企业部署不产生长期客户专属分支。
- [ ] 租户隔离覆盖数据库、缓存、队列、检索、对象和日志。
- [ ] 软件开发和短视频均有真实 E2E 证据。
- [ ] 每个 Task 的质量、耗时、费用和失败原因可查询。
