# 房间首局等待 300 秒自动解散实现报告

## 实现结论

房间创建后，以服务端权威路由表的 `created_at` 为唯一计时起点。只要第一局从未开始，数据库时间达到 300 秒即由 Gateway 生命周期任务发起自动解散。加入、退出、准备、状态刷新、断线和重连均不修改该时间。

首局开始由 `first_round_started_at` 永久标记。该标记与首局状态快照在同一个数据库事务中提交，之后即使玩法状态进入局间等待，也不再参与首局等待超时。首局开始提交还带有数据库时间边界：到达 300 秒后不能再获得“首局已开始”最终状态。

## 权威状态机

```text
CREATING / RECOVERING
          │
          ▼
       ACTIVE
          │
          ├─ 首局在 300 秒内开始 ─► ACTIVE + first_round_started_at（永久豁免）
          │
          └─ 300 秒到期且首局未开始
                    │ 原子条件更新：ACTIVE 且 first_round_started_at 为空
                    ▼
                 REMOVING
                    │ 大厅幂等关闭、成员离房、票据删除、在线推送
                    ▼
                  REMOVED + 删除可恢复快照
```

到期与首局开始竞争同一条房间权威路由记录。到期转换要求 `ACTIVE`、正确 fencing token、`first_round_started_at IS NULL` 且数据库时间已经达到 `created_at + 300 秒`；首局开始转换要求仍为 `ACTIVE` 且数据库时间尚未到期。两者只能有一个提交成功。

## 资源与恢复闭环

- 自动解散请求号固定为 `waiting-room-expiration-{roomId}`，大厅关闭重复执行仍返回已解散结果。
- 大厅关闭事务将房间置为 `DISSOLVED`，把 `JOINING/JOINED` membership 置为 `LEFT`，并删除该房间的游戏票据，因此 join、ticket、active-room 和继续恢复入口不再成立。
- Gateway 在大厅关闭成功后移除内存运行态，并在同一数据库事务中把路由置为 `REMOVED`、删除 `aoo_room_snapshot` 可恢复快照。
- 若进程在 `REMOVING` 阶段退出，启动恢复任务会依据持久化请求号继续调用大厅幂等关闭；成功后再原子完成 `REMOVED + 快照删除`。
- 服务重启不会重置计时。恢复时沿用路由表原始 `created_at` 和 `first_round_started_at`，生命周期任务按数据库中已消耗的时间继续计算。
- 在线连接收到 `common.room.auto_dissolved`，客户端清除房间恢复意图与权威房间缓存，显示“房间超过300秒未开始，已自动解散”，并回到大厅状态。
