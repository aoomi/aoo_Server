# 跑得快业务编码与房间历史清理运行手册（2026-09-07）

## 目标与边界

迁移 `V20260907_03__pdk_business_codes_and_room_history_cleanup.sql` 将成都、内江、凉山跑得快的稳定业务编码收敛为 `CD201`、`NJ201`、`LS201`，并按用户明确授权一次性清理全部历史和活动房间。

迁移保留账号、认证、钱包、`aoo_ledger`、亲友圈主体与成员、订单和运营配置。`aoo_room_billing_reservation` 属于房间运行态，会被删除；账务流水不删除、不改写。`aoo_room_id_sequence` 保留，避免复用曾经进入账务流水的房间号。

## 审计与事务

- `aoo_room_history_cleanup_run` 固化保留域迁移前后行数与执行状态。
- `aoo_room_history_cleanup_count` 对每张清理表记录 `BEFORE`、`AFTER` 的精确行数和过滤条件。
- 房间、成员、路由、快照、事件、幂等、结算、回放清单/分片/短码以及房间派生数据在一个显式事务中按依赖顺序清理。
- append-only 表的删除门禁只在当前迁移连接设置 `@aoo_authorized_room_cleanup=1` 时放行；普通连接仍然 fail-closed。
- 事务提交前强制断言：所有目标余量为零、三个目录编码正确、当前发布快照没有旧编码、账号/账本/亲友圈主体及成员行数不变。

## 生产执行流程

1. 进入维护窗口，禁止 Hall、Gateway 和游戏节点创建或写入房间。
2. 对权威 MySQL 做可恢复备份，记录 GTID/快照点和副本延迟。
3. 先查询迁移目标表的精确计数，和迁移内 `BEFORE` 审计口径逐项核对。
4. 仅通过项目 Flyway 入口执行迁移；不得复制 SQL 到远端手工拆段执行。
5. 查询审计结果：

```sql
SELECT * FROM aoo_room_history_cleanup_run
WHERE run_id='20260907-pdk-code-reset-v1';

SELECT phase,table_name,row_filter,row_count
FROM aoo_room_history_cleanup_count
WHERE run_id='20260907-pdk-code-reset-v1'
ORDER BY table_name,phase;
```

6. 确认 `AFTER` 全为零，三个 `aoo_game_catalog.game_code` 分别为 `CD201/NJ201/LS201`，且 `aoo_compiled_index_active` 指向的新 release 快照一致。
7. 启动服务后，先验证目录只返回三个独立条目，再各创建一个测试房间验证独立规则和协议路由；测试房间验收后按正式清理接口移除。

## 回退

清理提交后不能用逆向 SQL 恢复房间历史，只能从步骤 2 的数据库备份恢复到新实例，再按事故变更流程切换。不得用重新插入部分事件、伪造回放清单或重置 `aoo_room_id_sequence` 的方式回退。

本次任务只允许在本机/测试库实际执行；本文档不代表已操作任何生产或远端数据库。
