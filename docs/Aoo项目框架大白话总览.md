# Aoo 项目框架大白话总览

这份文档给不懂代码的人看。它只解释项目现在是怎么分工、数据怎么流动、遇到需求应该找哪里。具体技术细节仍以各专项规范为准。

项目未来要发展成什么、现有文档有哪些问题，请继续读 [Aoo 项目发展愿景与框架文档审计](./Aoo项目发展愿景与框架文档审计.md)。

AI 如何统一调度、怎样建立任务卡和判定完成，请读 [AI 统一调度与任务验收规则](./项目管理/AI统一调度与任务验收规则.md)。当前任务只以 [当前任务看板](./当前状态/当前任务看板.md) 为准。

## 1. 先用一句话看懂整个项目

Aoo 是一套棋牌游戏系统，主要由三部分组成：

- **客户端 Client**：玩家看到和点击的界面。
- **服务端 Server**：判断操作是否合法、保存房间状态、计算输赢。
- **管理后台 Admin**：运营人员查看和管理玩家、亲友圈、房间、玩法配置与发布记录。

可以把它想成一家餐厅：

- 客户端是前台和菜单，负责展示与接收点单。
- 服务端是厨房，决定订单能不能做，并产出最终结果。
- 管理后台是店长办公室，负责配置菜单、查询订单和处理运营问题。

最重要的一条：**客户端不能自己决定牌局结果，最终结果必须由服务端确认。**

## 2. 项目顶层结构

```text
Aoo/
├── Client/   玩家客户端，Cocos Creator 3.8.8 + TypeScript
├── Server/   登录、网关、大厅、房间、玩法和数据服务
├── Admin/    管理后台
└── AGENTS.md 所有 AI 都必须遵守的项目总规则
```

三个目录分别是独立 Git 仓库，日常开发都使用 `develop` 分支。没有用户明确要求时，AI 不得自行提交或推送。

## 3. 客户端怎么分

客户端主要目录：

```text
Client/assets/
├── Common/       全项目都会用到的公共能力
├── Login/        登录界面和登录流程
├── Lobby/        游戏大厅
├── Club/         亲友圈、联盟相关界面
├── Modules/      可独立划分的业务模块
└── Games/
    ├── Common/   所有游戏房间都会用到的能力
    ├── Mahjong/  麻将大类
    ├── Poker/    扑克大类
    ├── LongCard/ 长牌大类
    └── WordCard/ 字牌大类
```

### 3.1 公共层和玩法层有什么区别

公共层只放真正能被多个业务复用的东西。

例子：

- 网络请求、加载提示、公共头像属于全项目公共层。
- 扑克牌牌面、扑克小结算属于扑克公共层。
- 成都跑得快特有规则只属于成都跑得快，不能塞进公共层。

依赖方向只能是：

```text
具体玩法 -> 牌类公共层 -> 全项目公共层
```

不能反过来。比如公共头像组件不能去引用成都跑得快，否则其他游戏也会被迫加载成都跑得快。

### 3.2 Prefab、Scene、Bundle 是什么

- **Scene**：一个完整场景，例如登录场景、主场景。
- **Prefab**：可以重复使用的一块界面，例如玩家头像、数字键盘、小结算面板。
- **Bundle**：一包可以独立下载和加载的资源。
- **Atlas**：把很多小图片装进一张大图，减少绘制和加载次数。
- **`.meta` / UUID**：Creator 给资源的身份证。移动资源时要保留，不能随便重建。

简单例子：玩家进入跑得快房间时，不应该把麻将、牛牛、金花的全部资源一起下载，只加载公共房间、扑克公共资源和当前跑得快资源即可。

## 4. 服务端怎么分

本地核心服务可以理解为几道关卡：

```text
玩家
  -> Gateway 网关
  -> Account 账号服务
  -> Hall 大厅服务
  -> Room Authority 房间权威服务
  -> 对应玩法逻辑
  -> 数据库
```

各部分职责：

| 部分 | 大白话说明 |
|---|---|
| Version | 判断客户端版本能不能继续使用 |
| Account | 注册、登录、账号身份和会话 |
| Gateway | 玩家访问服务端的统一入口，负责转发消息 |
| Hall | 大厅、玩法目录、创建和加入房间入口 |
| Room Authority | 房间当前状态的最终裁判 |
| GameProvider | 提供某个玩法真正的规则实现 |
| Database | 保存账号、房间、战绩、规则版本等长期数据 |

### 4.1 为什么要有“权威服务”

防止不同玩家看到不同结果，也防止客户端作弊。

例如玩家点击“出 3”：

1. 客户端只上报“我要出这张牌”。
2. 服务端检查是不是轮到他、这张牌是否在手里、牌型是否合法。
3. 服务端更新房间状态并通知所有玩家。
4. 客户端按照服务端结果播放出牌动画。

客户端不能先把牌删掉，再要求服务端接受这个结果。

## 5. 管理后台负责什么

管理后台面向运营、客服、测试和管理员，目标是让日常管理不需要改代码。

主要职责包括：

- 玩家、账号和权限查询。
- 亲友圈、联盟、成员与房费管理。
- 房间、战绩、回放和异常查询。
- 玩法、地区、创建房间规则和发布版本管理。
- 操作审计：谁在什么时候改了什么。

后台不是第二套游戏服务。它可以发出管理命令，但不能绕过服务端直接改正在进行的牌局结果。

## 6. 开房配置表怎么工作

开房配置表位于：

```text
Client/docs/开房规则表/
```

这些表由用户维护，是“玩家创建房间时能看到哪些选项、默认选什么”的权威来源。

基本链路：

```text
用户维护 Excel
  -> 发布器读取并校验
  -> 生成稳定的机器配置
  -> 发布到数据库
  -> 客户端显示创建房间选项
  -> 服务端按相同规则执行
```

举例：表里写“必须出黑桃 3”，机器配置保存的不能只是显示文字，而要保存稳定键 `require_spade_three`。以后文字改成“首出黑桃3”，稳定键不变，服务端仍知道它是哪条规则。

规则表不能为了迁就代码而随意改含义。表和代码不一致时，通常应修正发布器、客户端或服务端实现。

## 7. 一个玩家从登录到结算经历什么

### 7.1 登录

```text
玩家输入账号
  -> Account 验证身份
  -> 返回会话
  -> 客户端进入大厅
```

### 7.2 创建房间

```text
客户端读取已发布玩法目录
  -> 展示开房选项
  -> 玩家选择规则
  -> Hall 校验玩法和规则版本
  -> Room Authority 创建房间
  -> 返回房间号和权威状态
```

### 7.3 进入并游戏

```text
玩家进入房间
  -> 客户端加载当前玩法资源
  -> 服务端下发完整房间状态
  -> 玩家进行坐下、准备或玩法操作
  -> 每次操作由服务端检查并广播
```

不同玩法可以有不同流程。例如扯旋、牛牛、金花没有单独准备步骤，玩家点空座坐下后默认准备。这个差异应由玩法流程表达，不应该复制整套公共房间。

### 7.4 小结算和大结算

- **小结算**：一局结束后的结果。
- **大结算**：整个房间全部局数或时间结束后的总结果。

服务端负责算分并保存结果；客户端只负责把结果正确展示出来。

## 8. 玩法如何分类

每个玩法都有稳定的 `game_code`，相当于玩法身份证。

现有重要编码示例：

| 编码 | 玩法 |
|---|---|
| `CD201` | 成都跑得快 |
| `NJ201` | 内江跑得快 |
| `LS201` | 凉山跑得快 |
| `CD299` | 成都扯旋 |
| `CN298` | 全国牛牛 |
| `CN297` | 全国金花 |

`CD` 表示成都，`CN` 表示全国。编码不能跟着界面显示名称变化，也不能同时再造一套 `pdk`、`chengdu-pdk` 等别名。

## 9. 状态机是什么

状态机就是“事情必须按什么顺序发生”。

一局游戏可以简化为：

```text
等待玩家 -> 开局 -> 发牌 -> 玩家操作 -> 小结算 -> 下一局或大结算
```

它像红绿灯：当前是红灯时，不能直接跳到通行；当前还没发牌时，也不能接受玩家出牌。

断线重连不是重新开始游戏，而是客户端重新取得服务端当前权威状态，再恢复到正确阶段。

## 10. 协议是什么

协议是客户端和服务端共同遵守的消息格式。

例如客户端发送：

```json
{
  "roomId": "755365",
  "action": "play_cards",
  "cards": ["S3"]
}
```

服务端返回是否成功、最新状态版本和所有玩家需要看到的变化。字段名称、含义和版本必须两边一致，不能只改一边。

## 11. 资源为什么不能随便移动

Creator 的 Scene、Prefab、图片和脚本之间不只靠文件路径关联，还会使用 UUID。直接在文件管理器里移动或重建 `.meta`，可能出现：

- 图片变成空白。
- Prefab 组件丢失。
- 脚本显示 Missing。
- 编辑器里仍看到旧内容。

因此资源变更后必须让 Creator 正常重新导入，并重新打开目标 Scene 或 Prefab 检查。

## 12. 出问题时先看哪一层

| 现象 | 优先检查 |
|---|---|
| 按钮点了没反应 | 客户端节点、按钮绑定、控制器日志 |
| 规则勾选后不生效 | 配置表、发布器、稳定键、服务端规则读取 |
| 玩家之间状态不一致 | 房间权威状态、消息版本、广播流程 |
| 算分不对 | 服务端玩法规则和结算逻辑 |
| 图片或 Prefab 丢失 | `.meta`、UUID、Bundle、Creator 导入状态 |
| 登录超时 | Gateway、Account、网络地址和服务健康状态 |
| 重连后界面不对 | 服务端权威快照和客户端恢复流程 |

## 13. 一个需求应该改哪里

| 需求 | 主要责任位置 |
|---|---|
| 调整按钮位置、颜色、图片 | Client 对应 Scene/Prefab/UI 资源 |
| 修改玩家可选的开房项 | 开房规则表，再走发布链路 |
| 修改牌型、合法性或算分 | Server 对应玩法逻辑 |
| 增加一种玩法独有表现 | Client 对应玩法目录 |
| 多个扑克玩法共用的牌面能力 | Client 扑克公共层 |
| 查询或管理亲友圈数据 | Admin + Server 亲友圈接口 |
| 修改账号登录流程 | Client Login + Server Account/Gateway |

一个需求可能跨前后端，但每一层只做自己的职责。不要为了让界面暂时看起来正确，就在客户端复制一份服务端规则。

## 14. 当前开发红线

- 不修改其他项目，只处理 Aoo。
- 不让客户端决定牌局合法性和最终得分。
- 不复制公共实现到每个地区玩法。
- 不用临时 `if/else` 一层层绕过根因。
- 不随意重建 `.meta` 或 UUID。
- 不直接修改运行中的房间规则。
- 不把密码、Token、密钥写进代码、日志或 Git。
- 没有用户明确指令，不提交或推送 Git；每日固定快照任务除外。
- 配置表、客户端、服务端和后台不能各维护一套互相矛盾的规则。

## 15. 非技术人员推荐阅读顺序

1. 先读本文，理解全项目地图。
2. 要看界面和资源规则，读 `Client/docs/前端框架规范/README.md`。
3. 要看具体开房选项，直接看 `Client/docs/开房规则表`。
4. 要看服务如何启动，读 `Server/docs/本地核心服务启动说明.md`。
5. 要看某次修复是否真的验证过，再查 `Server/docs/verification` 和各类验收报告。

历史记录和验证报告是“证据库”，不是框架入门教材；只有排查对应问题时才需要阅读。
