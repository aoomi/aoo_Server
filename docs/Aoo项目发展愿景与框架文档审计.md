# Aoo 项目发展愿景与框架文档审计

本文回答两个问题：

1. 现有框架文档哪里清楚、哪里混乱、以后怎样维护。
2. Aoo 项目以后要发展成什么，以及应该按什么顺序建设。

本文不代表所有功能已经完成。凡是写“愿景”“目标”“规划”的内容，都必须经过开发和真实验收后，才能改成“已完成”。

## 1. 项目愿景

Aoo 不只是做一个能开房的棋牌游戏客户端，而是要形成一套长期可扩展、可运营、可验证的棋牌游戏平台。

最终希望达到：

- 玩家可以稳定完成登录、大厅、亲友圈、创建房间、完整游戏、大小结算、战绩和回放。
- 新玩法主要增加自己的规则和表现，不再复制一整套登录、大厅、房间和结算框架。
- 产品人员通过配置表和后台管理玩法，不需要频繁修改底层代码。
- 每项规则都能说清楚来源，每次发布都能追踪，每个异常都能通过日志定位。
- AI 员工按职责协作，但不能越权修改、静默停止或自己宣布验收通过。
- 项目上线后能承受真实用户、亲友圈、房间、账务和长期运行压力。

一句话总结：**先把每个游戏真实跑通，再把共同能力做稳，最后把它建设成可配置、可运营、可持续增加玩法的平台。**

## 2. 用户已经明确的产品方向

根据当前项目要求，以下方向已经比较稳定：

### 2.1 游戏必须真实可玩

“代码存在”不算完成，“能创建房间”也不算完成。一个玩法至少要真实走通：

```text
玩法选择
-> 创建房间
-> 多名真人账号加入
-> 坐下/准备或玩法自己的开局方式
-> 发牌
-> 全部操作
-> 正确算分
-> 小结算
-> 下一局
-> 大结算
-> 战绩和回放
```

断线重连、退出、解散、超时、异常操作也要有明确结果。

### 2.2 XQP 是玩法对照，不是直接复制旧工程

扯旋、牛牛、金花和跑得快等玩法需要深入对照 XQP 的业务流程、显示时间、清理步骤、开房选项和算分规则。

“等价移植”的含义是玩家体验和业务结果等价，但代码必须按照 Aoo 当前框架重新组织，不能把旧项目整套结构原样塞进来。

### 2.3 公共能力只做一份

登录、大厅、亲友圈、公共房间、头像、聊天、网络、结算基础结构属于公共能力。玩法只实现自己的真实差异。

例子：

- 所有扑克都要显示牌面，牌面基础能力放扑克公共层。
- 只有凉山跑得快需要摆牌区，就由凉山配置开启对应节点。
- 其他跑得快不应该复制一份公共房间，只为了隐藏摆牌区。

### 2.4 横屏链路优先

现阶段先把横屏从创建房间到大小结算全部跑通，再建设竖屏。不能横竖屏同时半成品，导致两个方向都无法完整验收。

### 2.5 规则由一条权威链路发布

用户维护开房规则表，系统负责校验、生成稳定键、发布版本并让客户端和服务端共同使用。显示文字可以改变，稳定业务编码和稳定规则键不能跟着变化。

### 2.6 AI 是开发员工，不是无约束自动修改器

每个 AI 应有清楚的岗位、目录边界、测试账号和验收责任。AI 可以主动排查和解决职责范围内的问题，但：

- 不能修改其他玩法或共享框架来绕过问题。
- 不能用补丁堆叠掩盖根因。
- 遇到真正阻塞必须报告。
- 功能完成需要真实证据。
- Git 推送必须遵守用户授权和固定快照规则。

## 3. 发展路线

### 第一阶段：先做到“真实能玩”

当前最重要的阶段，不追求一次把所有平台能力做满。

目标：

- 登录、大厅和服务器入口稳定。
- 亲友圈基础流程可用。
- 成都、内江、凉山等跑得快链路真实跑通。
- 扯旋 `CD299`、牛牛 `CN298`、金花 `CN297` 横屏完整跑通。
- 创建房间选项、玩法流程、算分、大小结算与 XQP 对照一致。
- 服务端异常、客户端报错和关键业务动作有可检索日志。

完成标准：不是 AI 说完成，而是使用真实账号从用户界面完整玩完，并保存房间号、日志、截图、网络记录和结算结果。

### 第二阶段：做到“稳定复用”

目标：

- 清理玩法之间的复制代码和重复资源。
- 公共房间、扑克公共层、结算和资源生命周期稳定。
- 断线重连、重复点击、迟到消息、服务重启和资源释放可验证。
- 规则发布、玩法注册、客户端显示和服务端执行保持一致。
- 横屏稳定后补齐竖屏适配。
- 自动测试覆盖规则、流程和算分，真实 E2E 覆盖最终用户链路。

完成标准：新增同类玩法时，主要工作是增加玩法规则、差异配置和独有资源，而不是再复制一套框架。

### 第三阶段：做到“可以运营”

目标：

- 管理后台支持玩家、亲友圈、联盟、房间、战绩、回放和权限管理。
- 玩法规则支持草稿、审核、测试、发布、灰度和回滚。
- 房费、积分、结算与账务可以对账，不能重复扣费或重复结算。
- 客服操作有权限限制和审计记录。
- 监控登录、建房、入房、出牌、结算成功率和服务健康。

完成标准：普通运营工作不需要直接改数据库、服务器文件或源代码。

### 第四阶段：做到“可以上线和扩张”

目标：

- 正式域名、证书、WAF/CDN、备份和灾难恢复完整。
- 大规模账号、亲友圈和并发房间经过压力测试。
- 防作弊、暗牌隔离、回放权限和数据安全通过审计。
- 多节点服务故障后可以接管和恢复。
- 发布、回滚和数据迁移都有演练记录。

完成标准：在生产同规格环境完成性能、安全、恢复和长时间稳定性验收，而不是只在开发电脑上运行成功。

### 第五阶段：平台化和新的业务方向

棋牌游戏平台稳定后，可以把已经验证的 AI 调度、工具、审批、审计和工作流能力抽象为独立智能体平台，再支持软件开发、短视频工作流、企业智能体和个人 SaaS。

这一阶段必须与 Aoo 棋牌游戏运行框架分开：

- 棋牌游戏是当前产品。
- AI 智能体平台是未来可能形成的独立平台能力。
- 两者可以共享研发经验，但不能共用一套含义混乱的业务文档。

## 4. 当前框架文档审计结论

### 4.1 做得好的地方

- 客户端、服务端、管理后台文档已经按目录归档。
- 玩法编码、资源归属、服务端权威和真实 E2E 等核心原则明确。
- 大量修复和验证保留了证据，出现历史问题时可以追溯。
- 开房规则表有明确只读边界，避免 AI 随意修改用户配置。
- 对安全、幂等、房间状态、账务和资源生命周期已有较完整要求。

### 4.2 主要问题

#### 问题一：入门文档太少，技术细节太早出现

新人一打开文档就看到 Bundle、UUID、CAS、Outbox、fencing token 等词，很难先建立整体认识。

处理方式：已经新增 `Aoo项目框架大白话总览.md`，以后它是非技术人员第一入口。

#### 问题二：规范、现状、计划和历史证据混在同一篇文档

例如产品规范中夹着某一天某个 Controller 的测试结果；未来管理后台规划使用现在时描述，容易被误解为已经实现。

以后必须分为四种文档：

| 类型 | 只写什么 |
|---|---|
| 总览 | 普通人理解整体结构 |
| 规范 | 长期必须遵守的规则 |
| 现状 | 当前真实可用和未完成项 |
| 证据 | 某次测试、修复、截图、日志和报告 |

一篇文档尽量只属于一种类型。

#### 问题三：部分“当前”文档已经过期

`Aoo-当前剩余问题与处理任务清单.md` 标注更新时间为 `2026-08-24`，但项目已经发生大量后续变化。它仍声明自己是“当前唯一剩余任务入口”，这个说法需要重新核实后才能继续保留。

在重新盘点前，应把它当历史任务快照，而不是当前事实。

#### 问题四：完成状态存在层级混用

有些文档写“专项测试通过”，后面又写“真实 Canvas 验收未完成”；读者容易只看到前半句就认为功能完成。

以后统一使用：

- `代码完成`
- `自动测试通过`
- `Creator 同步完成`
- `真实 E2E 通过`
- `生产验收通过`

只有达到哪一级就写哪一级，不能统一写成“已完成”。

#### 问题五：管理后台规划容易被误认为现状

`棋牌游戏管理后台功能规划.md` 内容完整，但主要是目标设计，不代表后台已经具备全部能力。

建议长期保持标题和开头明显标注“规划”，并另建一份简短的“管理后台当前能力清单”。

#### 问题六：AI 平台文档与棋牌游戏框架并列，边界不清楚

`AI智能体平台架构与开发规范.md` 涵盖软件开发、短视频、企业 SaaS，这是未来独立平台愿景，不是当前棋牌游戏服务运行结构。

建议后续把它归入独立的“未来平台规划”目录；在尚未迁移前，阅读者不得把其中能力视为 Aoo 当前已实现功能。

#### 问题七：本地启动说明存在容易过期的具体描述

启动文档中包含具体文件名、账号范围、端口和一次性验证结果。这些内容变化快，长期规范和当前运行数据应该分开。

建议保留稳定启动命令，把账号初始化结果、某次端口状态和测试证据移到验证报告。

#### 问题八：产品规则文档夹带实现类名

产品文档应该说明玩家看到什么、操作后发生什么，不应该长期依赖 `LegacyClubMainController` 等具体类名。类名改动后，产品规则不应失效。

具体类名、测试文件和日期应放到对应验证报告，产品文档只保留稳定流程。

本次只提出整理方案，没有批量移动旧文件，避免破坏已有链接和 AI 引用。后续迁移应建立旧路径映射并逐批完成。

## 6. 文档以后怎么写

每份现状或验收文档开头建议固定写：

```text
文档类型：现状 / 规范 / 规划 / 验证证据
适用范围：客户端 / 服务端 / 管理后台 / 全项目
更新时间：YYYY-MM-DD
当前结论：一句话
不代表：明确排除容易误解的内容
```

规则：

- 总览用大白话，不贴大量源码和类名。
- 规范只写长期规则，不追加每日开发流水。
- 当前状态必须有更新时间，过期后降级为历史快照。
- 规划必须明确“尚未实现”。
- 验证报告必须写环境、版本、操作、结果和证据位置。
- 同一个结论只保留一个权威位置，其他文档用链接引用。
- 完成事项不继续留在“当前未完成任务”里。

## 7. 当前最值得优先做的事情

按项目愿景和现状，建议优先级如下：

1. 先维护一份真实的“当前功能状态表”，停止依赖旧日期任务清单。
2. 横屏跑通现阶段重点玩法的创建、游戏、大小结算完整链路。
3. 对照 XQP 建立逐项规则和体验差异表，避免只凭感觉说等价。
4. 修正规则表、发布器、客户端和服务端之间的不一致。
5. 在真实可玩基础上整理公共层，避免边开发边大范围重构。
6. 建立管理后台当前能力清单，再按运营价值补功能。
7. 最后进行竖屏、性能、安全、生产部署和平台化建设。

## 8. 判断项目是否在正确方向上的五个问题

每次准备做较大改动前，可以先问：

1. 这个改动让玩家完整流程更接近真实可玩吗？
2. 它是在修根因，还是又增加一层补丁？
3. 这是公共能力，还是真正的玩法差异？
4. 客户端、服务端、配置和数据库是否仍只有一个权威答案？
5. 完成结论是否有真实用户操作证据，而不只是代码和自动测试？

五个问题都能回答清楚，项目通常就在正确方向上。
